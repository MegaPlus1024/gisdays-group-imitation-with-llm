# Отчёт о системе автономных LLM-агентов

## 1. Назначение

Проект проверяет, может ли локальная языковая модель действовать как участник
контролируемого рабочего процесса, а не только отвечать на одиночный вопрос.
Модель получает роль, ограниченный набор инструментов, локальные данные и
критерии завершения.

Основные исследовательские вопросы:

- может ли локальная LLM выполнять роль работника;
- могут ли несколько агентов согласованно завершить общий процесс;
- соблюдаются ли права, зависимости и полномочия источников;
- сохраняются ли точные значения при передаче между ролями;
- восстанавливается ли агент после неудачного действия;
- сохраняется ли корректность на длинной траектории.

Runtime не доверяет свободному тексту модели как команде. Каждый ход должен
содержать один структурированный Action. До выполнения проверяются имя
инструмента, роль, параметры, путь, состояние зависимостей и история повторов.

Проект предназначен для исследования контролируемых внутренних workflow.
Он не является системой общего доступа к компьютеру или интернету.

## 2. Архитектура

### Runtime

Канонический runtime находится в
`src/agent/autonomous_multi_agent_runtime.py`.

Он отвечает за:

- загрузку профилей агентов;
- создание независимого состояния каждого агента;
- логическое round-robin чередование;
- передачу текущего observation в model policy;
- проверку и выполнение одного Action;
- обновление локальной и групповой истории;
- применение лимитов ходов и повторов;
- определение terminal state;
- формирование итоговой сводки.

`AgentState` содержит профиль, память, историю, последнее observation и статус
завершения. История одного агента не подменяет историю другого: общие данные
передаются только через зарегистрированные операции.

Round-robin является детерминированным порядком ходов. Это логическая
координация, а не одновременный inference нескольких моделей.

### Model policy

Model policy получает:

- профиль текущего агента;
- ограниченную память;
- доступные инструменты;
- текущее observation;
- релевантную историю;
- незавершённые требования.

Для локальной модели используется OpenAI-compatible endpoint на localhost.
Контракт ответа допускает один JSON Action на ход. Модель выбирает действие,
но не выполняет его сама.

Детерминированные fake policies позволяют проверить runtime, сценарии и
метрики без модели и HTTP-вызовов.

### Tool registry

`ToolRegistry` хранит описание каждого инструмента и его executor.

Канонический набор включает:

- чтение локальной статьи;
- поиск и извлечение значения из статьи;
- чтение и запись файлов в разрешённых границах;
- ограниченные операции с office fixtures;
- публикацию и чтение общего факта;
- ожидание зависимости;
- проверку точного значения и полномочий;
- завершение задачи агента.

Перед dispatch runtime проверяет, разрешён ли инструмент роли и соответствует
ли Action схеме. File tools дополнительно применяют политику относительных
путей и разрешённых рабочих корней.

### Shared environment

Общая среда содержит:

- локальные fixture-файлы;
- опубликованные факты;
- provenance каждого факта;
- описания ресурсов;
- состояния зависимостей;
- completion requirements;
- наблюдаемое evidence.

Публикация факта не сводится к записи строки. Runtime может потребовать
конкретный источник, evidence id, точное нормализованное значение и роль с
соответствующим authority.

### Validation and guards

Основные проверки:

| Проверка | Назначение |
| --- | --- |
| role permission | запрещает инструмент вне allowlist роли |
| Action schema | отклоняет malformed JSON и неизвестные параметры |
| path policy | блокирует абсолютные и выходящие за рабочий корень пути |
| grounding | связывает опубликованный факт с наблюдённым evidence |
| exact value | запрещает сокращение или перефразирование требуемого значения |
| authority | проверяет допустимый источник и роль |
| dependency wait | разрешает ожидание только объявленной зависимости |
| repetition guard | останавливает неизменный неуспешный повтор |
| finish guard | не позволяет завершиться при невыполненных требованиях |
| retention | проверяет сохранение нескольких фактов на длинной траектории |

Ошибка инструмента возвращается как структурированное observation. Следующий
ход может исправить действие, если лимиты и repetition guard это допускают.

### Evidence

Каждый запуск может создать:

- `experiment_summary.json`;
- `trial_summary.json`;
- `group_trace.jsonl`;
- рабочие файлы сценария;
- resource samples в JSONL и CSV;
- server stdout/stderr;
- evidence manifest с SHA-256.

Trace хранит переходы состояния, Actions, результаты инструментов и
диагностику протокола в ограниченном и sanitised виде.

### Поток выполнения

```text
LLM policy
    |
JSON action
    |
runtime validation
    |
tool execution
    |
shared state / files / facts
    |
next observation
```

## 3. Benchmark

Полный benchmark содержит семь сценариев и пять повторов каждого сценария.
Один запуск модели состоит из 35 испытаний.

| № | Сценарий | Идентификатор | Что проверяется |
| ---: | --- | --- | --- |
| 1 | Извлечение данных и передача файла | `article_file_handoff_v2` | Один агент извлекает значение из локальной статьи, другой использует подтверждённый результат и создаёт требуемый файл. |
| 2 | Восстановление после отсутствующего файла | `office_shared_fact_recovery_v2` | Агент получает ожидаемую ошибку чтения, выбирает корректный источник и публикует общий факт для следующей роли. |
| 3 | Границы ролей и точная передача идентификатора | `role_boundary_exact_handoff` | Только роль с нужными полномочиями может выполнить действие, а идентификатор должен быть передан без изменения. |
| 4 | Исправление некорректного действия | `malformed_action_recovery` | Первая попытка нарушает контракт; последующий ход должен исправить форму Action и продолжить процесс. |
| 5 | Конфликт между источниками | `conflicting_grounded_facts` | Агенты должны выбрать авторитетный источник и не публиковать неподтверждённое значение. |
| 6 | Зависимости и защита от раннего завершения | `dependency_progress_and_finish_guard` | Агент ждёт объявленный ресурс, продолжает после прогресса другой роли и не завершает задачу раньше времени. |
| 7 | Длительный многофакторный workflow | `long_horizon_multi_fact_retention` | Несколько агентов сохраняют факты, создают файлы, проходят recovery, разрешают конфликт и подтверждают итоговый снимок состояния. |

Сценарии используют локальные fixtures. Внешний интернет и реальные
пользовательские системы в benchmark не вызываются.

## 4. Условия прохождения

Модель считается прошедшей полный набор только при одновременном выполнении
всех обязательных условий.

| Условие | Порог |
| --- | ---: |
| Успешные испытания | не менее 32/35 |
| Минимум в каждом сценарии | не менее 4/5 |
| Grounded requirements | 100% |
| Нарушения ролей | 0 |
| Ungrounded publications | 0 |
| Неизменные неуспешные повторы | 0 |
| Recovery success rate | не менее 90% |
| Точность exact values | 100% |
| Wrong-authority publications | 0 |
| Undeclared waits | 0 |

Высокая общая сумма не компенсирует провал обязательного сценария. Поэтому
результат 30/35 с нулём в длительном сценарии не проходит итоговый критерий.

## 5. Результаты

### Поведенческая проверка

| Модель | Общий результат | Длительный сценарий | Обязательный критерий |
| --- | ---: | ---: | --- |
| `third_model` | 30/35 | 0/5 | не пройден |
| `fourth_model` | 30/35 | 0/5 | не пройден |
| `fifth_model` | 30/35 | 0/5 | не пройден |
| Qwen3.6-27B Q5_K_M | 35/35 | 5/5 | пройден |

Три исходные модели прошли все короткие и средние сценарии по пять раз, но не
завершили ни одного повтора длинного многофакторного workflow.

Qwen3.6-27B Q5_K_M прошла все 35 испытаний, включая пять повторов длинного
сценария. Дополнительный запуск использовал те же определения сценариев,
критерии и scoring. Model-specific упрощения prompt или evaluator не
применялись.

Correctness-first сравнение ставит Qwen на первое место в пределах этого
benchmark. Исходный зафиксированный результат трёх моделей при этом не
переписывается и остаётся отдельной линией evidence.

Эти цифры не являются общей оценкой интеллектуальных способностей моделей.
Они относятся к конкретному набору локальных fixture-задач и строгому Action
protocol.

## 6. Результаты измерения ресурсов

Ресурсные значения взяты из проверенного сравнения lifecycle-owned запусков.
Каждый профиль использовал один `llama-server`, одну модель, context 12288,
один parallel slot, три warmup-запроса и по десять измеряемых запросов трёх
размеров.

### Qwen3.6-27B Q5_K_M

| Метрика | Значение |
| --- | ---: |
| GGUF | 19,509,790,944 bytes |
| Loaded-idle VRAM | 19,386 MiB |
| Peak VRAM | 19,410 MiB |
| VRAM headroom | 5,057 MiB |
| Short mean latency | 2,970 ms |
| Medium mean latency | 7,031 ms |
| Long mean latency | 13,250 ms |
| Peak power | 148.43 W |
| Peak temperature | 87°C |
| Измеренные запросы | 30/30 |
| Offloaded GPU layers | 65/65 |

Профиль измерен на NVIDIA RTX PRO 4000 Blackwell с 24,467 MiB доступной
памяти. Это описание одной машины, а не универсальное требование.

### Сравнение профилей

| Наблюдение | Модель |
| --- | --- |
| Наименьший loaded-idle и peak VRAM | `third_model` |
| Наибольший VRAM headroom | `third_model` |
| Наименьшая short/medium/long latency | `fifth_model` |
| Наименьший peak power | `fifth_model` |
| Наименьшая peak temperature | `fifth_model` |
| Единственная прошла обязательный correctness criterion | Qwen3.6-27B Q5_K_M |

`fifth_model` была быстрее и холоднее в измеренном resource workload.
`third_model` требовала меньше памяти. Qwen потребовала больше ресурсов, но
единственная завершила весь поведенческий набор.

Общий синтетический resource score не вычисляется: latency, память,
температура и корректность отвечают на разные вопросы.

## 7. Насколько benchmark похож на реальную работу

### Хорошо моделируется

- разделение обязанностей между ролями;
- работа с документами и structured facts;
- передача точных идентификаторов;
- зависимость одного работника от результата другого;
- approvals и authority источника;
- исправление действий после ошибки;
- audit trail каждого хода;
- строгие критерии завершения.

### Не моделируется полностью

- человеческая социальная динамика;
- открытый интернет и произвольные сайты;
- неоднозначные или меняющиеся цели;
- свободное формирование команды;
- настоящий параллелизм inference;
- работа, продолжающаяся дни;
- multi-user production load;
- production incident response и security review.

Fixture-среда делает эксперимент повторяемым, но одновременно ограничивает
обобщение результата на реальные организации.

## 8. Практический вывод

Архитектура подходит как исследовательская основа для контролируемых
внутренних workflow, где инструменты и данные можно заранее ограничить.

Надёжность обеспечивается не одной моделью. Для неё нужны runtime guards,
provenance, точные completion requirements и проверяемый trace.

Сильная локальная модель может пройти полный многоагентный сценарий, но цена
по памяти и времени остаётся существенной. Результаты одного GPU и одного
пользователя нельзя использовать как production capacity estimate.

Benchmark не доказывает production readiness, безопасность произвольного
окружения или устойчивость к неизвестным задачам.
